# Limitations and confounders

This document lists every known difference between the three branches that is not the protocol itself, every known bias of the instruments, and the open issues of the third-party implementations that affect results. A comparison made with the testbed should declare the ones that apply to it. Each item states whether it was **measured** in the testbed or **read from the source code** of a component, and under which versions; version numbers are the pinned defaults unless stated otherwise (see [deployment.md](deployment.md) for how to change them). The CSV records most of the conditions involved, so that results with different conditions are never mixed ([measurement.md](measurement.md)).

## What is being compared

- **Implementations, not protocols.** The testbed measures dash.js (5.2.1), `@moq/watch` (npm 0.6.3 by default, or a git commit) with the moq relay and publisher, and the browser's WebRTC stack with mediasoup (3.32.1) or MediaMTX (1.21.3), not LL-DASH, MoQ and WebRTC in the abstract. Other implementations would behave differently, and results obtained with different versions are not comparable with each other (the `versions` column records them).
- **Stock behaviour.** No player, relay or publisher is modified to improve its results. Every option that does modify one is a declared experiment, off by default, recorded in the CSV ([adaptation-and-experiments.md](adaptation-and-experiments.md)).
- **Only the server–browser leg is emulated.** Ingest (orchestrator → Nginx, relay or SFU) uses the internal network.

## Transport and congestion control

- **Congestion control differs.** DASH runs over Linux TCP with CUBIC (and RACK); the MoQ relay runs QUIC with BBRv3 (`noq` in the published relay); WebRTC uses the receiver-driven estimators of mediasoup (or none, with MediaMTX). The testbed does not change any of them.
- **Netem jitter reorders packets and penalises almost only QUIC** (measured). With 150 ± 50 ms, 79-80 % of packets arrive out of order. The relay's QUIC stack (`noq` 1.3.0) uses the fixed RFC 9002 reordering threshold of 3 packets and its BBRv3 cuts the window when loss in a round exceeds 2 %: 36 % of packets were declared lost by reordering (none actually lost) and MoQ received 7-8 fps, while TCP adapted its threshold and DASH received 60 fps. On real networks delay varies mostly in queues, which do not reorder. Read every MoQ result with jitter in this light ([network-emulation.md](network-emulation.md#jitter-reorders-packets)).
- **Rate limiter.** With the default `tbf` limiter, a single packet leaves without waiting after an idle period; `netem rate` paces every packet. This changes the BBR estimate of the relay built from moq `main` ([below](#moq-bandwidth-estimate)) and changes the network of all branches, so measurements with different limiters are not comparable. Declare it (`net_down_shaper`, `net_up_shaper`).
- **Bottleneck queue length.** Keyframe bursts overflow short queues; WebRTC, which forwards keyframes unpaced, is the most affected (measured with a 100 ms queue at 8 Mbit/s: 12.5 % loss with MediaMTX and 3.4 % with mediasoup, against 0.26 % for MoQ and 0.03 % for DASH). The default is 300 ms (RFC 8867). Declare it (`net_down_queue_ms`, `net_up_queue_ms`).
- **Relay certificate.** The relay uses either a self-signed certificate pinned by fingerprint in local mode, or a CA-issued (Let's Encrypt) certificate whose chain WebTransport validates in server mode ([deployment.md](deployment.md#the-two-modes)). It is a measurement condition; it can affect at most the QUIC handshake.
- **macOS hosts.** With Docker Desktop on macOS, the client's TCP endpoint is Docker Desktop's proxy, not the browser: for DASH the emulated connection is proxy–Nginx (the server-side congestion control is still the real one). QUIC and WebRTC are not affected. On a Linux host this does not happen.
- **The client's own network.** Absolute figures depend on the network between the client and the server (Wi-Fi or VPN links add bursts). To compare versions or settings, alternate the variants in the same session and use WebRTC as a control.

## Quality adaptation

- **Where adaptation is decided.** In DASH and MoQ the player decides; in WebRTC with mediasoup the SFU decides; with `RTC_SERVER=mediamtx` WebRTC has no adaptation and always serves the top rendition (`rtc_server` in the CSV). mediasoup runs inside a minimal application of the testbed (`sfu/server.mjs`) with RTP ingest, not WHIP, which would be the usual ingest for an SFU; the layer decision is mediasoup's, with its defaults.
- **Bitrate each player compares against.** MoQ compares with the catalog bitrate, which the publisher measures in 1 s windows and holds at its peak (measured about 1.85× nominal: 7.4-7.5 Mbit/s for 1080p@4000), so the `@moq/watch` 80 % rule needs an estimate above 9.3 Mbit/s to hold 1080p. DASH compares with the nominal bitrate of the MPD.
- **MoQ seamless switching can deadlock** (measured, `@moq/watch` `bc64b9c`). On a down-switch the old track keeps downloading at the same priority until the new one catches up; with the link full it never does, and the painted rendition stays at the top one while the selected one is low. `*_selected_height` and `*_height` are recorded separately for this reason.
- **dash.js throughput estimation** (read from the dash.js 5.2.1 code and measured). Without a bandwidth limit, chunks that arrive in under 1 ms are accumulated with the idle gap that follows, so the estimate follows the downloaded bitrate (about twice it) and not the network capacity; a local network also delivers chunks in under 1 ms. With 1-frame CMAF fragments the estimate overestimates even on a limited link (1.6-2× the link). With 100 ms fragments on a 4 Mbit/s link it was 1.2×. Any throughput-based rule then chooses above what fits.
- **L2A in dash.js 5.** It does not leave its start-up phase with targets under 1.5 s (read from `L2ARule.js`: it only switches to its algorithm when the buffer reaches the fixed 1.5 s `B_target`; until then it picks like the throughput rule); and its steady phase has a units bug (bit/s compared with kbit/s, present from 5.0.0 to at least 5.3.0) that makes it pick the highest rendition fitting the last throughput sample. The `l2afix` option is the declared experiment with the bug fixed.
- **LoL+ stays at the lowest rendition with low targets** (read from the dash.js 5.2.1 code): it estimates the download time of a whole 2 s segment, and with a buffer under about 0.6 s its `DWS_BUFFER_MIN` check always steps down.
- **In practice the DASH factory rules reduce to the throughput rule** with the testbed's MPD (read from the code): low-latency mode skips `insufficientBufferRule`, and BOLA only takes over with 12 s of buffer.

### MoQ bandwidth estimate

The estimate that `@moq/watch` uses to choose (`moq_bw_estimate_kbps`) comes from the relay and depends on its version:

- **Published relay (0.17.9, and up to 0.17.16)** (read from the code and measured): the transport `web-transport-moq` 1.3.5 computes it as `cwnd × 8 / RTT`, the BBRv3 window over the RTT, not a measured rate. BBR keeps a window of about twice the bandwidth-delay product, so the estimate is about 1.7-2× the link with realistic delay (20 ms), and tens or hundreds of times the link with `delay_ms: 0` and a loose link (300 Mbit/s median on a 10 Mbit/s link). MoQ then picks 1080p where it does not fit.
- **Relay built from moq `main` (commit `c19c723`)**: the figure is BBR's `max_bw`. With a base delay of 2.5 ms or more it matches the link; without delay it inflates (3× the link at 2 Mbit/s, with selected renditions that are never painted, `moq_selected_height` ≠ `moq_height`). Measured inside the relay: with the `tbf` limiter a single packet passes without waiting after an idle period and, with BBR's minimum RTT at about 0.1 ms, its filter does not discard that sample. With the `netem rate` limiter it does not inflate without delay (1.1× at 2 Mbit/s, 1.0× at 10 Mbit/s).

With either relay, declare the base delay of the network and the limiter in every comparison, and use a base delay with the `main` relay or state that there is none.

### WebRTC: mediasoup underestimates the link

mediasoup tends to underestimate the downlink and stay at low layers (measured; mediasoup 3.32.1, default settings). Two causes were identified: after a loss its loss-based controller only lets the estimate rise to 1.5× what has been acknowledged, which at 360p is low, so it does not leave it; and even without losses the unpaced keyframe bursts appear to trigger overuse in its delay-based estimator (deduction). It climbs back very slowly once a limit is removed, and if the estimate falls below the lowest layer's bitrate it stops sending video until the player's watchdog recreates the session (about 11 s), so WebRTC stall time includes testbed-driven reconnections. The result depends on the router queue and on the GOP: declare both. The ingest pacer (`rtc_pacing`, declared experiment) removes most queue drops but not the low-layer choice, and delays keyframes.

### No encoder feedback loop in WebRTC

The three branches receive the same broadcast-style stream: H.264 Constrained Baseline without B-frames, a keyframe every GOP (1 s by default) and capped bitrate (120 % of nominal, 1 s buffer). That is what services ingesting WebRTC from an external encoder (WHIP) recommend, but not how WebRTC encodes in a video call, where libwebrtc uses a constant bitrate adjusted live by congestion control, a keyframe interval of 3000 frames and extra keyframes when the receiver asks for them after a loss (read from the libwebrtc sources; the standard only fixes the codecs, RFC 7742). Here nobody serves the keyframe requests (PLI/FIR) of the browser: mediasoup sends them and the testbed's RTP relay drops them, and MediaMTX forwards what it receives. After a loss, or after a layer switch, the picture only recovers at the next IDR (up to 1 s with the default GOP), and no encoder lowers its rate under congestion. DASH and MoQ do not need this loop because they adapt by choosing among pre-encoded renditions. The fixed GOP is the right choice for the comparison (DASH segments and MoQ groups start at keyframes), but **WebRTC is measured in conditions different from its usual use**, especially with loss or limited bandwidth. Measuring it as in a video call would require a sender that serves receiver feedback (a browser or a libwebrtc-based sender), which would break the identical stream and would be a separate, declared experiment. With the ingest pacer off, keyframes of all renditions also arrive at the same time and unpaced.

## Latency and buffering

- **The target-latency sliders mean different things.** DASH: dash.js `liveDelay`, chased with LoL+ catch-up, plus **Seek to live** (`maxDrift`) and **Minimum buffer** (`playbackBufferMin`). MoQ: `@moq/watch` `delay`, to which the library adds the catalog's track jitter. WebRTC: `jitterBufferTarget`, a hint to the browser. Comparing latencies is, to a large extent, comparing buffer configurations, and the buffer of each branch is of a different order (in one reference configuration, about 2.8 s for DASH, 200 ms for MoQ and 55-95 ms for WebRTC; see [protocols/README.md](protocols/README.md)).
- **DASH does not adapt its target to network delay** (read from the dash.js 5.2.1 code and measured): `liveDelay` is fixed at start-up; with network delay above what the target allows, dash.js accelerates, empties the buffer and stalls. WebRTC sizes its buffer from the measured jitter and MoQ from the RTT, so they raise their latency on their own. A comparison at equal network profile must choose and declare the DASH target for that profile (or measure, per profile, the minimum target without freezes).
- **MoQ `auto` delay depends on the `@moq/watch` version.** In 0.6.3 (read from the code and measured) it is computed from the RTT reported by the relay (1.25 × the minimum, with a 20 ms floor) and never rises during a session, because the minimum RTT is kept as a running minimum: after changing the network profile the page must be reloaded for it to be recomputed. In commit `bc64b9c` it adapts during the session with a NetEq-like estimator (95th percentile of frame lateness, about 2 s ceiling), and retransmitted frames count as late, so losses also raise it.
- **Reading MPEG-TS costs a different number of frames in each branch, and falls in different stages** (measured at 60 fps). From the arrival of a frame's last packet until it leaves packaged: MediaMTX 17 ms (1 frame), the MoQ publisher 34 ms (2 frames, relay included) and FFmpeg 50.5 ms (3 frames). The frame inherent to the format is paid by all three; the rest is per implementation. In DASH that time falls in the "CMAF packaging" stage, in MoQ and WebRTC it is hidden in "Publishing and transport". The input stage (time the frame waits at the gate) is comparable across branches and so is the total latency; the following stages are not ([latency-measurement.md](latency-measurement.md)).
- **DASH clock sync crosses the emulated network.** dash.js synchronises its clock with `UTCTiming` through the router, like the media, and takes the server time as the midpoint of the request, compensating half its round trip. When the two directions take different times (different delay down and up, or the reply waiting in the downlink queue behind video) the clock is off by half the difference, and dash.js computes segment availability and live latency with that error. The latency measured by the dashboard is not affected: its own clock (`/api/time`) does not cross the router.
- **WebRTC stage split.** In WebRTC, the split of the breakdown between "transport" and "buffer" is not reliable (`receiveTime`).
- **MoQ declared vs measured latency.** A gap of about 200 ms between MoQ's measured and declared latency is not yet attributed; repeating the measurement with hardware decoding is pending.
- **Joining a WebRTC stream at its very start** leaves the video 45-55 ms higher for the whole session (measured; what sends the first second of media at once is not located). The dashboard waits until the packager has been running for 8 s before connecting, which is what any viewer joining a running live stream experiences.

## Audio

- **Who carries audio.** DASH always downloads the audio Representation; MoQ only subscribes to the audio track when its player has the sound on (`@moq/watch`); WebRTC has no audio unless `rtc_audio` is enabled. Only one player has the sound on at a time (`audio` in the CSV).
- **WebRTC with audio** synchronises the video to the audio jitter buffer: little effect with the looped file (audio target about 40 ms), 100-200 ms more with the camera (measured). Recorded in `rtc_audio`.
- **Sound in MoQ.** With the sound on MoQ, latency was the same in three of five windows and higher (127 and 157 ms against 83-89) in two (measured with the camera at 15 fps). In headless Chrome there is no speaker: audio plays to a null output.

## Source, content and server load

- **Content.** Big Buck Bunny (60 fps) is the default. **Tears of Steel** changes content and frame rate at once (24 fps: 41.7 ms frames, so latency resolution, a "1-frame" fragment and the 1-3 frames retained at the input all last 2.5 times longer; each frame has 2.5 times more bits at the same bitrate; the 150 ms stall threshold is 3.6 frames instead of 9; deduced, not measured). With the **camera** as source the content does not repeat (tests are not comparable with the loop or with each other; within one test the three branches see exactly the same), the measured latency starts at the burnt-in timecode and excludes the camera → server leg, the input is irregular (WebRTC sees it as arrival jitter and its buffer grows), and camera clock drift shows in `dash_availability_drift_ms`.
- **MoQ publisher ingest** (measured). The published `moq-cli` 0.14.x releases (0.14.7 is the default pin) do not process more than about 2 MB/s of input (about 0.3 µs of CPU per byte, mostly in the kernel), with `import ts` as with `import avc3` and without viewers. Each keyframe (~100 kB) holds it about 50 ms; with one rendition there is one gap per group (from about 45 ms to several hundred ms on a loaded machine). With a three-rendition ladder it saturates (95th-percentile input wait of 0.6-0.7 s), adds hundreds of ms to MoQ latency and causes most of the catalog `stalled` marks and of the quality switches seen with `@moq/watch` 0.6.x; halving the ladder bitrate removes two thirds of them. The function responsible inside `moq-cli` is not identified (the binary has no symbols). moq `main` does not have the limit (200-730 MB/s measured at commit `bc64b9c`); build the publisher with `MOQ_CLI_FROM=git` to avoid it. Before trusting another `moq-cli` version, measure its input with a viewer connected (`POST /api/trace`) and check that it starts (`restarts.moq` in `GET /api/status`).
- **Source lag with a ladder.** With the three-rendition ladder, the server's source can fall behind real time at times, and the three players see it as lower latency. It is measured every second (`source_lag_ms`); check it before interpreting a latency below the target.
- **Shared encoder process.** Every output of the master FFmpeg advances in lockstep, so any new output (e.g. the camera reference for VMAF) can hold back the ladder; measure the encoder delay with and without it (`POST /api/trace`).
- **CPU load.** Three 1080p60 renditions plus two players on the same machine bring it close to saturation.

## Client and measurement environment

- **The meter must not disturb what it measures.** Instrumentation in the browser is asynchronous and cheap by design; a timecode reader that copies whole frames saturates the main thread and degrades MoQ. The main-thread load of each worker is recorded ([measurement.md](measurement.md)).
- **`@moq/watch` memory.** `@moq/watch` keeps its buffer as decoded frames (about 280 MB at 1080p with a 1.5 s buffer). On workers with little memory (measured with 1 GB of RAM and 512 MB of swap) the browser pages to swap and the main thread stops, only in MoQ and only at 1080p with targets of 1.5 s or more; those MoQ tests are not reliable. The fix is more memory for the workers.
- **Players in the same browser** share the main thread, the decoder, the CPU and the client connection. Campaigns can run one player per test (`player_mode: "each"`) or one independent worker per player ([campaigns.md](campaigns.md)).
- **Parallel tests share the server.** Tests of one batch share relay, SFU, publisher, origin, CPU, source and the server's physical link, though not the router queue or the browser, and a protocol may be measured on different machines over a campaign. Each test records with which others it ran (`batch`, `concurrent`, `concurrent_players`, `parallel`) and its worker's IP.
- **Queues are per protocol, not per viewer.** Outside parallel campaign tests, two tabs (or a leftover headless browser) playing the same protocol share its emulated link. Before measuring with a bandwidth limit, check in `GET /api/status` that the protocol's counter is not rising, and close every headless browser after each run.
- **Per-client slots are keyed by IP.** Two workers behind the same IP never run at the same time; a test whose traffic does not cross its worker's slot is invalid.
- **Underpowered workers.** A worker without a GPU (for example 2 vCPU) cannot sustain three 1080p60 players at once, and the validity check does not catch it: check `fps_measured`, the presented frames and the main-thread load of each worker ([campaigns.md](campaigns.md)).
- **Headless browsers** render with their own 60 Hz rhythm and, without a GPU, composite in software; `--software-decode` in the worker script also changes the video decoder. Declare the kind of worker (headless or kiosk, GPU or not) with the results.
- **Restarts.** A session with pipeline or player restarts is not a clean measurement (`pipeline_restarts`, `dash_player_restarts`, `moq_player_restarts`).

## Operational caveats

- **Restarting the router** loses the applied network profile (back to unrestricted) and resets its counters.
- **Not available:** time-varying network profiles (traces or scheduled steps), a shared-link mode to study competition between protocols, and a client outside the host on macOS so that TCP is end to end.
